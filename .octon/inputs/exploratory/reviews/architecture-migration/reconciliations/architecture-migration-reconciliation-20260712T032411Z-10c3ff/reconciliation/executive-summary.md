# Reconciled Executive Summary

## Bottom line

Octon's proposed target architecture is the right direction for materially improving the solo-developer experience, but neither original migration program should be implemented unchanged. The sound core is: one candidate-immutable authority path, credentialless isolated candidates, one local transactional store, one supervised local broker, sanitized privileged Git, independent exact-SHA verification, recoverable Class B publication, signed bounded evidence, safe self-development, and minimal project/harness/extension/child-agent layers.

The reconciliation verdict is **READY_FOR_PROPOSAL_PROGRAM**. This means the target and safe migration are sufficiently established to author the formal program. It does not mean the current repository is safe for privileged autonomous implementation, no-PR Class B publication, trust-root automation, or promoted support claims.

## Where the reviews agree

Both reviews establish that Octon already contains valuable typed authority, lifecycle, context, route, support-target, provider-adapter, evidence, extension-publication, and promotion primitives. Both also establish that current behavior does not prove the accepted target: launch authority is split; candidates share credential-capable host and Git state; no accepted broker or authoritative SQLite store exists; provider writers and verifiers execute candidate-controlled code; direct-main remains reachable; recovery/evidence is non-transactional; and trust-root activation is absent.

## What reconciliation changed

The reconciled program adds four load-bearing corrections:

1. Canonical mediation is insufficient unless the authorization evaluator, policy, interface inputs, decision binary, and executed receipt code are candidate-immutable. Production runner/bin/mode/stale-route overrides must not weaken authority.
2. The candidate boundary requires an independent repository/object database, not an ordinary linked worktree. Useful model authentication must also work without exposing durable credentials.
3. No-PR publication requires a server-observed expected-old, fast-forward-only update. Current check-then-push logic can miss an intervening target move that remains an ancestor of the source.
4. Broker supervision, credential enrollment, status, doctor, repair, and restart/reconciliation ship with the broker, while tracked run-state and workflow burden receive explicit migration owners.

The reconciliation rejects full-store deferral, plain Git anchoring instead of signed observations, minimal Workspace Project deferral, unsafe rollback to ambient Git/YAML/log-only privilege, linked-worktree-only isolation, and claims that the existing route bundle or provider manifests already complete FD-020 or FD-023.

## Smallest safe program

The retained sequence is containment first, then authority and isolation, then one store and broker, sanitized Git and immutable verification, signed evidence and recovery, complete Class B proof, trust-root activation, Projects/Harness Factory/mission inbox, private extensions and bounded children, and finally end-to-end solo dogfood and promotion. Fourteen workgroups coordinate fifteen proposal packets so that extensions, child-agent safety, and final support promotion have separate sources of truth without adding runtime components. The operator sees five value milestones and one Solo Local profile, not packet/workgroup machinery.

## Expected solo-developer effect

If the reconciled program closes its proof gates, Octon should materially improve autonomous completion and delivery speed while lowering routine review and recovery burden: routine Class A/B prompts become zero, broker failures reconcile automatically, PRs become deterministic escalations rather than the only lane, raw evidence leaves project Git, and setup/doctor/repair become one-command operations. If the proof gates or burden budgets fail, the architecture must not be promoted merely because its components exist.
