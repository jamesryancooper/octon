## Findings Addressed

### AR-001 (critical) — promotion targets fail canonical validation

- **Previous position:** `proposal.yml#promotion_targets` listed the two broad
  roots `.octon/state/` and `.octon/generated/`, and
  `target-architecture.md#File-Level Work Areas` listed the same two roots as
  the only work areas.
- **Defect:** `validate-proposal-standard.sh` hard-failed (errors=2, baseline
  run pre-revision): `.octon/generated/` contains the generated proposal
  registry, which references this packet's own proposal path, tripping the
  proposal-path backreference rule (validate-proposal-standard.sh:434-472);
  `.octon/state/` failed the same rule via retained evidence files. Broad
  operational roots can never satisfy that rule, and they also violated
  child-packet-contract item 11.
- **Revised position:** `promotion_targets` now names the exact deliverables
  from the parent registry write scopes plus the child evidence root:
  - `.octon/framework/assurance/runtime/_ops/scripts/validate-octon-storage-migration.sh`
  - `.octon/framework/assurance/runtime/_ops/tests/test-octon-storage-migration.sh`
  - `.octon/framework/assurance/runtime/_ops/fixtures/octon-storage-migration/`
  - `.octon/framework/constitution/contracts/retention/octon-storage-migration-allowlist-v1.yml`
  - `.octon/state/evidence/validation/proposals/public-distribution-self-hosting-octon-storage-migration/`
  `target-architecture.md` now names every registry-scoped deliverable and
  explains that `.octon/state/` and `.octon/generated/` remain the packet's
  operational surface via the parent registry write-scope locks: the
  index-state migration operations there are journaled operations against
  mutable or rebuildable content, not durable owned content, so they are not
  promotion targets. `implementation-plan.md` phases now deliver each named
  target explicitly.
- **Why this improves alignment:** the packet now passes canonical validation,
  conforms to child-packet-contract item 11, and separates durable owned
  deliverables (validator, test, fixtures, allowlist contract, evidence) from
  journaled operational effects, which is the distinction the promotion model
  exists to enforce.

### AR-008 (major) — declared sensitivity control had no validation home

- **Previous position:** the negative control "No raw sensitive content
  appears in receipts" was asserted in `target-architecture.md` with no
  deterministic check, no fixtures, and no acceptance criterion; migration
  logs were named in Security And Publication Implications but not in the
  control.
- **Revised position:** the control now reads "receipts or migration logs"
  and is enforced by a leak/denylist check in
  `validate-octon-storage-migration.sh` with checked-in sensitive and clean
  fixtures under
  `.octon/framework/assurance/runtime/_ops/fixtures/octon-storage-migration/`.
  Added to Proposed Components, Deterministic Automation, the Validation Plan
  (validator and test-harness lines), and new acceptance criterion AC-07
  (fail on sensitive fixtures, pass on clean fixtures, pass on every actual
  receipt and log).
- **Why this improves alignment:** a declared security control without a
  negative test is an assertion, not a control; the check now has a durable
  implementation home, checked-in evidence of both directions, and a closeout
  gate.

### AR-011 (minor) — subjective acceptance-criterion language

- **Previous position:** AC-02 gated on "High-value raw evidence" with no
  definition source, leaving a subjective run-time judgment; AC-06 gated on a
  "representative migration batch" with no objective coverage rule.
- **Revised position:** AC-02 defines high-value raw evidence solely by the
  enumeration in
  `.octon/framework/constitution/contracts/retention/octon-storage-migration-allowlist-v1.yml`,
  with no subjective judgment at run time. AC-06 requires the rollback batch
  to cover every storage class named in the allowlist contract at least once.
  AC-05, the Validation Plan restore and keep-set lines, Proposed Components,
  Ownership, and Maintainer-Only Authority now name the allowlist contract as
  the definition source for the keep-set and its enumeration as the
  maintainer-approval object.
- **Why this improves alignment:** acceptance criteria are now deterministic
  and checkable by the delivered validator, and maintainer authority attaches
  to an explicit enumerated artifact instead of an undefined category.
