## AR-011 — Objective acceptance tests for AC-01 and AC-05

Previous position (AC-01): "A machine-readable component graph identifies the
smallest dependency-closed base for the promised installation, bootstrap,
execution, validation, update, and rollback workflows." — "smallest" had no
objective test, so any dependency-closed selection could pass.

Revised position (AC-01): minimality is objectively testable — the selected
closure must equal the transitive dependency closure of the declared
entrypoint components recorded in `.octon/framework/manifest.yml`; nothing
outside the computed closure may be selected, and nothing inside the
selection may be unreachable from a declared entrypoint. The validator fails
on either deviation.

Previous position (AC-05): "A basic name-conflict search receipt and concise
official-identity input exist, while unresolved plausible conflict blocks
maintainer clearance." — the receipt had no defined fields and "plausible
conflict" had no definition, so both the receipt and the blocking condition
were unverifiable.

Revised position (AC-05): the receipt must record the exact queries run, the
sources searched, the search date, the results found, and the maintainer
disposition for each result. A blocking conflict is defined as any active
project, product, organization, or registered mark using the same or a
confusingly similar name in the software tooling or agent-framework space
whose result the maintainer has not dispositioned as non-conflicting; any
undispositioned plausible conflict blocks clearance.

Why this improves alignment: both criteria now have deterministic pass/fail
conditions that a verification route can check against retained receipts
instead of relying on judgment words.
