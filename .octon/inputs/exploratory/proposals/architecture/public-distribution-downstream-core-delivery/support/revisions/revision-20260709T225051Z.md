## Findings Addressed

### AR-002 — Promotion targets narrowed to exact registry deliverables

- **Previous position:** `proposal.yml#promotion_targets` listed five broad
  framework directories (`.octon/framework/engine/runtime/spec/`,
  `.octon/framework/engine/runtime/crates/`,
  `.octon/framework/scaffolding/runtime/`,
  `.octon/framework/assurance/runtime/_ops/scripts/`,
  `.octon/framework/assurance/runtime/_ops/tests/`), and the
  target-architecture File-Level Work Areas repeated the same five broad
  paths without naming any deliverable file.
- **Revised position:** `promotion_targets` now lists the exact deliverable
  files and leaf directories from the parent-registry write scopes
  (`spec/downstream-core-delivery-v1.md`, `crates/core_delivery/`,
  `scaffolding/runtime/templates/octon/`,
  `scaffolding/runtime/_ops/scripts/init-project.sh`,
  `validate-downstream-core-delivery.sh`,
  `test-downstream-core-delivery.sh`) plus the child evidence root
  `.octon/state/evidence/validation/proposals/public-distribution-downstream-core-delivery/`.
  The target-architecture work areas name every registry-scoped deliverable
  explicitly with its role and whether it is new or an existing surface being
  modified.
- **Why this improves alignment:** It satisfies parent child-packet-contract
  item 11, removes the packet's claim over sibling-owned files inside the
  shared assurance and scaffolding directories, and makes promotion scope
  auditable file-by-file against the registry.

### AR-007 — Change-level rollback made distinct from runtime rollback

- **Previous position:** The only rollback content was the
  "Rollback And Interrupted Operation" section of the implementation plan,
  which describes the delivered tool's runtime rollback inside a downstream
  target. The registry `rollback_posture: rollback-route` had no change-level
  counterpart, and nothing stated that `init-project.sh` already exists.
- **Revised position:** The implementation plan gains a
  "Change-Level Rollback Of This Packet's Promotion" section: `init-project.sh`
  is an existing script being modified, not created, and `templates/octon/` is
  an existing template tree being modified; each promotion target family lands
  as a single revertible promotion commit (scaffolding modifications, new
  engine deliverables, new assurance deliverables); the exact revert route for
  the scaffolding modifications is `git revert` of that family's promotion
  commit restoring prior bytes; after any revert the packet validators are
  re-run to prove a coherent pre-promotion state. The runtime rollback section
  now states explicitly that it covers the delivered tool only. The
  target-architecture work areas mark the existing-vs-new status of every
  deliverable.
- **Why this improves alignment:** The registry rollback posture is now
  backed by a concrete, executable change-level route instead of being
  conflated with the tool's own runtime rollback semantics, and modification
  of pre-existing scaffolding is no longer misrepresentable as file creation.

### AR-011 — AC-01 and AC-04 made externally defined and complete

- **Previous position:** AC-01 required an "accepted provenance identity"
  with no definition source. AC-04 required a "complete dry-run diff" without
  defining completeness.
- **Revised position:** AC-01 states that "accepted provenance identity" is
  defined by the portable-component-clearance-v1 clearance contract (owned by
  public-distribution-portable-base-clearance) and that this packet consumes
  that definition without redefining it. AC-04 defines dry-run diff
  completeness: every add, modify, and delete relative to the lock manifest is
  listed, and nothing outside that set is listed.
- **Why this improves alignment:** Both criteria become deterministically
  testable, and provenance acceptance has a single cross-packet definition
  source instead of a per-packet reinterpretation.

### PD-025 traceability — Named negative validation case added

- **Previous position:** The validation plan had no case covering the revised
  parent PD-025 acceptance test, which requires a downstream install fixture
  in this packet excluding every public-repository-only manifest entry.
- **Revised position:** The validation plan names negative case NV-PD-025:
  a downstream install fixture proves every manifest entry labeled
  public-repository-only is excluded from installation, with
  runtime-generated test data explicitly permitted inside the
  `test-downstream-core-delivery.sh` test scope. The test-harness work area
  in the target architecture records the same.
- **Why this improves alignment:** The child now carries the validation
  obligation the revised parent traceability assigns it, at a named,
  checkable case rather than an implied one.
