# Layered Trusted Computing Base

## Decision Summary

Octon's trusted computing base is not a fixed list of seven components. It is a
profile-dependent set of components grouped by the security property for which
they are trusted:

1. local effect enforcement;
2. identity, credential, and evidence integrity;
3. merge and provider enforcement;
4. build, release, installation, and update integrity; and
5. recovery and rollback.

The target minimizes both code and identities able to perform durable effects.
Planning, reasoning, project modeling, workflow selection, context assembly,
Project Profile construction, and harness compilation stay outside the
privileged TCB. They may propose and narrow inputs, but they do not receive
grant-signing keys, effect credentials, evidence-signing keys, provider write
credentials, or activation authority.

Every table below uses the same component contract:

- **trusted property**: the property whose correctness the architecture relies
  on;
- **privilege**: host or provider privilege the component needs;
- **credentials**: secrets, keys, leases, or identities it may possess;
- **modification authority**: who may change the component or its governing
  configuration;
- **effect authority**: durable effects the component may perform;
- **evidence authority**: claim-bearing evidence it may create;
- **update path**: how a new version becomes trusted;
- **verification method**: how the property is tested; and
- **compromise consequence**: the maximum credible impact if it fails or is
  malicious.

## Current-State Facts and Limits

These are repository facts, not target-state claims:

- The Rust runtime workspace contains `authority_engine`,
  `authorized_effects`, `lifecycle_executor`, `runtime_bus`, `replay_store`,
  `telemetry_sink`, `kernel`, and related crates. It contains no distinct
  effect-broker or evidence-signer crate
  (`.octon/framework/engine/runtime/crates/Cargo.toml:1-17`).
- The protected-CI command performs GitHub effects by invoking `gh` directly
  from the kernel process
  (`.octon/framework/engine/runtime/crates/kernel/src/commands/mod.rs:1542-1592`).
  The kernel, `gh`, its environment credential, the checked-out runtime source,
  the Actions runner, and GitHub therefore all participate in the effective
  current provider-effect TCB.
- The PR auto-merge workflow supplies `AUTONOMY_PAT || GITHUB_TOKEN`, checks out
  the pull-request head, and then runs the checked-out Octon wrapper/kernel
  (`.github/workflows/pr-auto-merge.yml:109-120,274-330`). Candidate code is
  consequently inside the credential-bearing provider-effect path today.
- The Run Journal uses SHA-256 sequence and hash-chain validation, but no
  separate signer, key custody, or external head anchor is implemented in the
  journal writer
  (`.octon/framework/engine/runtime/crates/runtime_bus/src/lib.rs:384-427,505-538,1658-1687`).
- Current constitutional ownership distinguishes human, harness, and model
  role classes, but it does not establish separately authenticated authority,
  broker, signer, verifier, executor, and child-agent process identities
  (`.octon/framework/constitution/ownership/roles.yml:3-78`).
- Self-evolution promotion is explicitly a readiness gate rather than a
  material writer, so the repository does not yet contain an independently
  installed activation authority
  (`.octon/framework/engine/runtime/spec/promotion-runtime-v1.md:3-11,30-35`).

These facts mean that the target inventories below are design requirements.
They must not be described as already deployed.

### Local-layer minimization

The model, orchestration workflow, Project Profile reader, effective-harness
compiler, prompt bundle, validation planner, and candidate Git process are not
in this TCB. They operate in disposable state and can fail without gaining a
durable credential. Hooks and in-process wrappers remain diagnostics and
defense in depth, not sole enforcement components.

The verifier App and effect App should be separate identities even if one human
owns both installations. A one-App deployment is a transitional profile only;
it must keep verifier code, token scopes, and merge adapter separated and must
not be described as two independent provider authorities.

## Profile Allocation

### Practical solo-developer default

- Rootless OCI sandbox (native Linux or VM-backed macOS/Windows) plus launch
  broker; an admitted native adapter is an optional fast profile.
- Per-user local broker outside the candidate sandbox.
- Platform keychain/vault and short-lived provider App tokens.
- Separate authority, broker, signer, verifier-App, and effect-App identities.
- Local transactional evidence store plus automatic remote signed-head anchor for
  Class B and Class C.
- Signed release slots with the immediately previous trusted version retained.
- One human operator; no routine second-person approval.

### Higher-assurance profile

- Dedicated lightweight VM plus privileged host sidecar.
- Hardware/KMS-backed authority, signer, release, and operator keys.
- Separate remote effect broker where the effect domain supports it.
- Dual external anchors or a transparency log.
- Stronger release quorum and optional two-person activation for selected Class
  C effects.
- Longer raw-evidence retention and independent restore drills.

## Update and Self-Protection Invariant

For any component in these inventories:

1. candidate implementation occurs without its production credentials;
2. the previously trusted version classifies and verifies the candidate;
3. the candidate is built and signed as an inactive release;
4. it cannot modify or control the only verifier, trust store, or activation
   gate approving it;
5. activation is a separate effect; and
6. the previous trusted version and recovery evidence remain available until
   the new version has passed the configured health and rollback window.

This invariant concentrates friction at trust-epoch changes. It does not add
per-action approval to ordinary Class A development or policy-allowed Class B
effects.
