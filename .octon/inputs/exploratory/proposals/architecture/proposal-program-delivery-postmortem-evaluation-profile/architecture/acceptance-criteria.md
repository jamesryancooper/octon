# Acceptance Criteria

- The lifecycle postmortem mechanism supports a proposal-program delivery evaluation profile for any completed proposal-program lifecycle.
- The profile preserves the existing generic postmortem evidence map, known limits, evaluator input, and structured report contract.
- The profile records proposal-program evidence binding for parent, child, retained index, planner, generated artifact, hygiene, delivery, and git proof refs where available.
- Blockers are classified by owning scope: parent program, child packet, linked proposal/change, generated artifact, lifecycle tooling or contract, worktree hygiene/residue, git/delivery state, prompt or authorization boundary, and external credential or permission boundary.
- Autonomy analysis separates deterministic low-risk governed recovery from human-gated material side effects.
- Efficiency diagnostics cover registry/freshness churn, stale digest churn, generated refresh timing, repeated planner single-blocker discovery, repeated operator continuation, and local executor/runtime failures.
- Delivery proof-chain audit covers archive, push, branch-no-PR landing, sync, cleanup authorization, branch cleanup, and cleaned claim when delivery evidence exists.
- Recommendation records include problem, proposed change, owning scope, expected autonomy or efficiency gain, safety rationale, risks, acceptance criteria, suggested validators/tests, and required governed route.
- Postmortem-to-proposal handoff output is evidence-only and cannot authorize implementation.
- Negative fixtures prove postmortem outputs cannot satisfy child-owned evidence or lifecycle transition gates.
