## Findings Addressed

### AR-004d: Pre-push public-remote guard lacked a durable home

- **Previous position:** The packet required "pre-push safety checks" and
  "pre-push protection against a public distribution remote" without naming a
  durable artifact. `proposal.yml#promotion_targets` listed eight targets
  (`.gitignore`, `.github/workflows/`, `CODEOWNERS`, `.codex/`, `.claude/`,
  `.cursor/`, `release-please-config.json`, `.release-please-manifest.json`)
  with no home for the hook. Target architecture said "Pre-push checks must
  inspect destination identity and fail closed for the public distribution
  from this workspace." Implementation plan phase 1 said "Add root-role
  detection, remote pre-push guard, and a dry-run tracking inventory." The
  validation plan said "A simulated push to the public distribution identity
  is rejected while approved private workspace destinations remain possible."
  AC-01 said "Workspace root policy identifies the repository as private
  self-hosting source and blocks pushes to the public distribution repository
  identity." `architecture-proposal.yml#affected_surfaces` listed
  "public-remote pre-push protection".
- **Revised position:** Added `".githooks/"` to `promotion_targets` (nine
  targets, matching the updated parent registry write scopes; the original
  eight are unchanged). Named `.githooks/pre-push` as the durable guard
  artifact in the target architecture (components, file-level work areas,
  security implications), implementation plan (phase 1 and validation plan),
  AC-01, README scope, and `affected_surfaces` (now ".githooks/ pre-push
  public-remote guard"). Noted that `core.hooksPath` activation is a manual
  migration step recorded in the run journal, and added the residual risk
  that a clone without the recorded activation step lacks the guard. The
  validation case is explicit in AC-01 and the validation plan: a simulated
  push to the public identity from the workspace is rejected by
  `.githooks/pre-push` while approved private destinations pass.
- **Why this improves alignment:** The guard now has a versioned, reviewable,
  promotable home inside the registry write scopes instead of an unlocated
  behavior, the manual activation gap is stated rather than implied, and the
  acceptance evidence for the guard is a concrete positive-and-negative case.

### AR-011: AC-04 and AC-05 asserted unenumerated classifications

- **Previous position:** AC-04 said ".codex, .claude, and .cursor are local
  or explicitly classified projections, and untracking preserves local files
  plus regeneration capability" without naming which content classes stay
  committed versus become local-only regenerable. AC-05 said ".gitignore
  expresses the approved local-first defaults and is in place before the
  Octon-internal storage migration begins" without enumerating the approved
  defaults.
- **Revised position:** AC-04 now enumerates the projection classification:
  the projected `commands/` and `skills/` trees under all three roots, plus
  the projected `rules/` trees under `.codex/` and `.cursor/`, become
  local-only regenerable and leave tracking; `.claude/settings.json` stays
  committed as hand-maintained workspace host policy;
  `.claude/settings.local.json` and `.codex/config.toml` remain machine-local
  and never tracked. AC-05 now enumerates the approved local-first defaults:
  `.codex/`, `.cursor/`, and `.claude/` (except `.claude/settings.json`)
  leave tracking, expressed by the ignore entries `/.codex/`, `/.cursor/`,
  and `/.claude/*` with the negation `!/.claude/settings.json`, with the
  existing `.codex/config.toml` entry subsumed and `.githooks/` remaining
  tracked with no ignore entry.
- **Why this improves alignment:** Both criteria are now deterministically
  checkable against named paths and ignore entries instead of deferring the
  classification to implementation-time judgment, which closes the gap
  between the acceptance gate and the actual migration decisions.
