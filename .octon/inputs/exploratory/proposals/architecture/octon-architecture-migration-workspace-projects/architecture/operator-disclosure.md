# Operator Disclosure

## Intended Solo Experience

The operator states intent from any adopted project. Octon identifies the
project, uses the saved correction-aware boundary and Profile, and freezes the
exact selection for the run. The operator does not choose an internal packet,
Harness route, or authority mechanism.

`octon mission inbox` provides one concise cross-project view. A normal row
contains project, mission, status, next action, and exact resume/status command.
Detailed continuity and evidence remain behind explicit inspection.

## When Octon Asks

One bounded question is allowed only when current evidence cannot safely
distinguish projects, resolve an undeclared overlap, or determine whether a
copied repository is a move or a new adoption. The answer becomes an operator
correction that future inference preserves.

Routine refresh, relocation, status, and inbox use require no approval prompt.
Any boundary-widening durable change still follows the applicable canonical
authority route; the project record does not authorize it.

## Failure Presentation

On failure, report:

- affected project and conflicting fact;
- whether active/candidate work is preserved;
- whether unrelated projects remain usable;
- the exact safe state retained; and
- the shortest repair or explicit correction command.

Do not expose schema rows, packet IDs, capability tokens, or registry internals
in the normal view.

## Claim Honesty

This draft makes no current onboarding, multi-project, or autonomy claim. The
five-minute onboarding and broader Solo Local budgets become eligible claims
only after RP-14 dogfood and promotion. Portfolio, team, and project-derived
authorization remain unsupported.
