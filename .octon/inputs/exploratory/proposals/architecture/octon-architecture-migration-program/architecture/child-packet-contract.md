# Child Packet Contract

Each child is a normal sibling proposal and independently owns its lifecycle,
promotion targets, implementation-grade receipt, review/authorization,
implementation, validation, proof, conformance, closeout, and archive metadata.
Parent evidence never satisfies a child receipt and no aggregate verdict changes
a child status.

Entry requires verified dependencies, stable baseline, exclusive exact source
ownership, resolved blocking RODs, rollback/recovery, and an accepted child.
Exit requires its FD/PO/PG and UE evidence, safe-state proof, authoritative
promotion, conformance/drift review, and child closeout. Shared physical files
use exact entry/module/symbol ownership and a serialized trusted integration
lane; sharing a file never means sharing semantic authority.

Children may not widen scope informally, create nested packets, absorb another
owner's semantics, use `.github/**` as an octon-internal target, claim planned
proof as executed, or treat generated/input/proposal/provider state as authority.
Material infeasibility returns to child revision and, only if the fixed boundary
cannot remain safe, parent program revision with operator disposition.
