## Findings Addressed

### AR-002 — promotion_targets must be exact registry-scoped deliverables

- **Previous position:** `proposal.yml#promotion_targets` listed
  `.octon/octon.yml`, `export-harness.sh`, and the two broad directories
  `.octon/framework/assurance/runtime/_ops/scripts/` and
  `.octon/framework/assurance/runtime/_ops/tests/`, which are far wider than
  this packet's registry write scopes and omit the child evidence root.
- **Revised position:** promotion_targets now name the exact deliverable
  files from the parent registry write scopes —
  `.octon/octon.yml`,
  `.octon/framework/orchestration/runtime/_ops/scripts/export-harness.sh`,
  `.octon/framework/assurance/runtime/_ops/scripts/validate-portable-dropin-export.sh`,
  `.octon/framework/assurance/runtime/_ops/tests/test-portable-dropin-export.sh`,
  `.octon/framework/assurance/runtime/_ops/scripts/validate-root-manifest-profiles.sh` —
  plus the child evidence root
  `.octon/state/evidence/validation/proposals/public-distribution-portable-dropin-export/`.
  The target-architecture File-Level Work Areas section names every
  registry-scoped deliverable, and the implementation plan phases name the
  two new validator/test filenames explicitly.
- **Why this improves alignment:** the packet can no longer claim durable
  authority over the whole assurance scripts and tests trees; its promotion
  surface now matches the parent's coordinated write scopes exactly and
  satisfies child-packet-contract item 11, including the octon-internal
  evidence-root requirement.

### AR-004c — AC-01 was unimplementable without amending the existing root-profile validator

- **Previous position:** AC-01 required portable_dropin to be "admitted by
  the root profile validator" without naming the validator or acknowledging
  that the existing
  `.octon/framework/assurance/runtime/_ops/scripts/validate-root-manifest-profiles.sh`
  hard-rejects any profile beyond bootstrap_core, repo_snapshot, pack_bundle,
  and full_fidelity, and that file was outside the packet's declared scope.
- **Revised position:** the parent registry now grants this packet write
  scope over `validate-root-manifest-profiles.sh`; AC-01 names that exact
  amendment, the implementation plan carries it as an explicit work item
  (phase 2), and both include the negative case that any other unknown
  profile name is still rejected. The target architecture records the
  amendment as a component, a work area, and a negative control.
- **Why this improves alignment:** AC-01 is now implementable within the
  packet's declared promotion targets, and the fail-closed posture of the
  existing validator is preserved rather than silently widened.

### AR-005 (supporting side) — PD-025 manifest labeling now owned here

- **Previous position:** the packet classified output as installable or
  public-repository-only in its scope statement, but the architecture carried
  no explicit PD-025 labeling mechanism, no acceptance criterion, and no
  validation case; parent traceability previously assigned PD-025 to
  public-distribution-public-repository-controls.
- **Revised position:** parent traceability now assigns PD-025 to this
  packet. The target architecture adds an installability-labeling component
  (every exported path carries exactly one manifest label, installable or
  public-repository-only, consumed downstream without redefinition), new
  AC-07 requires the labels with a fail-closed unlabeled-path case, and the
  validation plan adds the matching case: an export containing any unlabeled
  path fails closed.
- **Why this improves alignment:** the manifest is the single durable source
  of the installable versus public-repository-only distinction, matching the
  parent acceptance test for PD-025 and preventing downstream packets from
  redefining labels they should only consume.

### AR-011 — AC-06 "no workspace ancestry" lacked a measurement method

- **Previous position:** AC-06 read "A parity validator proves the public
  repository candidate tree contains exactly the manifest-declared public
  tree and no workspace ancestry." with no stated way to measure "no
  workspace ancestry".
- **Revised position:** AC-06 now states the concrete checks: the candidate
  tree contains no `.git` directory and no workspace commit references, and
  the staged import commit has no parent commit from the workspace history.
  The validation plan repeats the same measurable checks.
- **Why this improves alignment:** the criterion is now objectively
  verifiable at implementation time instead of relying on reviewer judgment
  of an undefined term.
