# Cutover Plan

## Cutover Profile

- release state: `pre-1.0`
- change profile: `atomic`
- atomic mode: one final private-release admission/publication model after
  bounded inert evidence stages

The stages do not create two publishers or two authority models. All private
imports remain denied until the accepted ROD-004 baseline is encoded and contracts are complete; verified
availability remains inert until exact desired/publication/Harness binding
activates.

## Stage 0 — Configuration and Dependency Admission

Encode the accepted ROD-004 baseline, verify RP-07/RP-11 exits, inventory all
writers/readers, and retain the safe default of private/external import denied.

## Stage 1 — Inert Contracts and Templates

Publish strict envelope, trust/pin, availability, state, generated, receipt,
and transition contracts. Align templates and governance without enabling
private import.

Safe resting point: current bundled publication continues; private import
denies because no live import route is admitted.

## Stage 2 — Verify-to-Availability Only

Enable safe signed import into retained immutable release plus availability/
quarantine/import evidence. Keep private desired selection and publication
disabled. Run signer/content/materialization and non-authority matrices.

Safe resting point: private releases can be inspected as available but cannot
be selected, published, resolved, compiled, or executed.

## Stage 3 — Exact Desired Pins, Publisher Disabled

Migrate desired config/trust policy and exact private pins. Publisher treats
private entries as ineligible while resolving/validation evidence is collected.

Safe resting point: desired intent exists, but actual/generated state remains
unchanged.

## Stage 4 — Publisher and Resolver Shadow

Stage complete active/quarantine/generated generations and verify resolver/
Harness identities without exposing private runtime use. Exercise revocation,
restore, interruption, and extension-disabled fallback.

Safe resting point: the single publisher proves coherent output but private
generation consumption remains off.

## Stage 5 — Atomic Private Generation Activation

Enable exact verified private pins, current publisher admission, strict
resolver checks, and RP-11 exact generation binding together. Simultaneously
make digest-only/acknowledgement-only external authenticity, floating private
selection, stale resolver use, and raw restore unreachable.

Safe resting point: one desired policy, one verified actual state, one
publisher, one generated generation, and one Harness binding govern private
extensions.

## Stage 6 — Retire Compatibility Paths

Retain bundled-first-party bridge, remove private/external legacy admission,
refresh projections, bound historical release retention through RP-07, and
scan durable targets for proposal references and unowned writers.

## Prohibited States

- import and selection/publication occur in one transaction;
- private content becomes active before intentional governed admission under
  ROD-004 or full verification;
- desired, availability, active/quarantine, or generated files have multiple
  writers or reverse authority edges;
- floating private version, unsigned external pack, or unapproved dependency
  can publish;
- current generation and Harness bind different release/payload identities;
- rollback rewinds/copies generated files without full current revalidation;
- public marketplace, auto-update, arbitrary-source fetch, second publisher,
  daemon, store, scheduler, or authority source appears; and
- RP-12 changes RP-07 signer/evidence or RP-11 Harness semantics.

## Promotion Handoff

After implementation proof, RP-12 supplies PO-FD-021, exact ROD-004 configuration/dependency
bindings, rollback posture, and bounded evidence to the canonical promotion
route. A signed-extension support claim remains optional and claim-scoped;
proposal prose is never copied into runtime authority.
