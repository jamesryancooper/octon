# Acceptance Criteria (Program Level)

Acceptance of this parent program means the suite design and coordination
structure are approved — not any child's content. The program is acceptable
when:

1. The child registry declares all seven children with canonical sibling
   paths, phases, dependencies, gates, write scopes, and required flags, and
   `related_proposals` matches the registry exactly.
2. The sequence encodes the real dependency chain (lens bank → taxonomy/
   routing → method docs + schemas → integration → conditional facades) as
   `verification` gates, with parallelism only inside phases.
3. Every intake element has a recorded disposition (accept / revise / merge
   / defer / reject) in `intake-evaluation.md`, every intake open question
   has an architect answer, and nothing is silently dropped.
4. The method taxonomy defines, for each of the six methods: slug, question,
   use cases, non-goals, required inputs, outputs, and escalation rules —
   with Balanced unchanged as default and Greenfield output bounded to
   reference architecture.
5. The lens bank design defines the full lens catalog once (ids, tiers,
   consolidation rationale), per-method required/optional profiles, the
   clean-sheet vs greenfield complementarity statement, and sprawl controls.
6. The disposition matrix classifies every required surface (methodology
   docs, review-routing.yml, naming.yml, readiness methodology,
   surface-audit doctrine, schemas/receipts, workflow contracts,
   validators/fixtures, command/skill facades, product feature catalog,
   generated projections, proposal lifecycle integration) as unchanged /
   extend / refactor-or-replace / proposal-only, with an owning child for
   every non-unchanged surface.
7. Authority boundaries hold everywhere: no new gate, mechanism, routed
   mode, or review-output authority; support receipt untouched; generated
   outputs derived-only; readiness and surface-audit doctrine unmodified;
   the intake unit cited as lineage only.
8. The child contract binds children to independent validity, own receipts,
   validation floors (negative controls where enforcement is touched,
   doc-consistency checks for doc-only children), suite design rules,
   write-scope discipline, and allowed terminal outcomes.
9. The closeout plan requires aggregate evidence outside proposal paths and
   records the two standing deferrals (command facades no-action default;
   Boundary/Authority generic mode) with owner and trigger.
10. The conditional child has an explicit no-action closure route so the
    program cannot stall on a decision that may legitimately be "not now".
11. Program validators pass: base proposal standard, architecture subtype,
    and program structure; the packet directory name equals the
    `proposal_id`.

Child acceptance criteria are defined per child at child creation; this
parent never substitutes for them. Per-child validation expectations are
summarized in `implementation-plan.md` and bound in the child contract.
