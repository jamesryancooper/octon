## 1. Purpose and Scope Boundary

This prompt orchestrates the **child lifecycles** of the Architecture Review
Method Suite Program. The parent implements nothing. "Program implementation" is
the coordinated execution of seven child-owned proposal packets, each of which
runs its own governed `create → review → accept → implement → verify → close`
lifecycle at its canonical sibling path
`.octon/inputs/exploratory/proposals/architecture/<child-id>/`.

The parent **coordinates**: it sequences children, enforces dependency gates and
write-scope discipline, records program-level coordination evidence, and closes
out once every registry child reaches an allowed terminal outcome. The parent
**does not own** any child manifest, receipt, promotion target, validation
verdict, or archive metadata, and its evidence never satisfies a child's.

Proposal readiness is permission to **orchestrate**, not proof that any child has
been implemented. Do **not** assume — or require as a precondition — that any
child's durable contracts, schemas, validators, fixtures, method docs, lens
bank, or canonical runtime support already exist. Each child produces them under
its own later, child-scoped authorization.

## 3. Parent-Owned Coordination Work

The parent's own work in this program is coordination only:

1. **Gate enforcement.** Keep both entry gates green before authorizing each
   child, and re-check the relevant dependency gate before a dependent child
   begins implementation.
2. **Sequencing.** Drive children through the phases and parallel groups in
   §5, honoring every hard dependency (`dependency_gate: verification`).
3. **Write-scope discipline.** Hold each child inside its registry-declared
   `write_scopes` (§4). A child that needs another child's scope requires a
   **registry revision at the parent**, not silent expansion, and never a
   coordinated changeset unless §5 explicitly requires one (it does not — every
   child owns an independent changeset here).
4. **Shared-surface coordination.** Serialize or partition writes to the shared
   methodology directory, shared validator-scripts directory, and shared
   assurance-contracts directory so parallel-group children never collide on the
   same file (§6).
5. **Program evidence.** Record program-level coordination evidence (per-child
   terminal outcomes, receipt paths + digests, disposition notes, deferral
   records) under the program evidence root (§8). Parent evidence points to child
   receipts by path and digest; it never copies, replaces, or substitutes them.
6. **Conditional child + deferrals.** Decide the conditional facades child on
   demonstrated operator demand and record the two standing deferrals at
   closeout (§7).
7. **Disposition handling.** On a blocked, rejected, or superseded required
   child, record the disposition and re-plan via registry revision or scope
   narrowing with rationale (§9).
8. **Run receipt.** Emit the parent-local run receipt at §10 after program
   execution.

The parent authorizes no effects of its own beyond coordination, mints no review
authority, creates no lifecycle gate/mechanism/workflow mode/command facade, and
does not implement, promote, publish, or archive any child surface.

## 5. Execution Sequence — Phases, Parallel Groups, Handoff Gates

Phases are operator pacing groups; **dependencies are the hard gates**. A child
with declared dependencies may not begin *implementation* until each dependency
passes its own `verification` gate (with child-owned receipts). Creation ahead of
gates is permitted; implementation ahead of gates is not.

- **Phase 0 — start immediately.** `architecture-lens-bank-foundation` (seed
  reference). Every method profile and method doc cites lens ids defined here, so
  this is the foundation.
  - **Handoff gate → Phase 1:** lens-bank child passes its verification loop.

- **Phase 1 — after the lens bank verifies.**
  `architecture-review-method-taxonomy-and-routing`. Naming v2 method entries and
  routing v2 method-selection semantics point at lens profiles that must already
  exist and validate.
  - **Handoff gate → Phase 2:** taxonomy-and-routing child passes verification.

- **Phase 2 — parallel group `method-docs` + `contracts-and-assurance`.** Once
  taxonomy-and-routing verifies, these three run **in parallel**:
  `greenfield-reference-architecture-review-method`,
  `companion-architecture-review-methods`,
  `architectural-review-schema-extensions`. They share the phase-1 dependency and
  write disjoint files (see §6), so no cross-child changeset is required or
  permitted.
  - **Handoff gate → Phase 3:** **all three** phase-2 children pass verification.

- **Phase 3 — group `integration`.** `architectural-review-suite-integration`
  (hard deps: all three phase-2 children) so workflow method-recording,
  feature/mechanism notes, lifecycle advisory text, projection refresh, and the
  closing validator sweep reflect the final landed docs and schemas. Then, only
  if operator demand is demonstrated, `architecture-review-command-facades` (hard
  dep: suite-integration).

Parallelism rule: a blocked or rejected child does **not** block siblings that
have no declared dependency on it; the parent records the disposition and
re-sequences via registry revision.

## 10. Terminal Criteria and Required Parent Run Receipt

**Program terminal criteria.** The program is ready to close only when:

1. Every **required** registry child reaches an allowed terminal outcome —
   `closed` (implemented + verified with child-owned receipts), `superseded`, or
   `rejected`.
2. The conditional `architecture-review-command-facades` child is either closed
   as a landed facade packet or recorded as **program-local no-action** with
   rationale.
3. Both standing deferrals (§7) are recorded with owner and re-trigger.
4. Aggregate program evidence is retained under the program evidence root (§8),
   pointing to child receipts by path and digest.
5. The parent run receipt below exists and is coherent.

Rejection of `architecture-lens-bank-foundation` or
`architecture-review-method-taxonomy-and-routing` invalidates the suite premise;
the expected disposition is program supersession or rejection, not scope
narrowing.

`support/program-implementation-orchestration-run.md` recording at least these
fields:

Use `verdict: pass` and `child_authority_preserved: yes` **only** when parent

never satisfies a child receipt, promotion target, validation verdict, or archive
metadata. If any required child is unresolved, or any child surface was
absorbed into the parent, record `verdict: fail` (or the accurate partial state)
and `child_authority_preserved: no` with the specific breach.

## 11. Authority Boundaries (fail-closed)

- Proposal packets, generated prompts, generated support files (including this
  one), the child registry, generated registries/projections, raw inputs, host
  state, chat, and model memory **do not** become Octon authority, control truth,
  runtime policy, or permission.
- Durable authority lands only in declared promotion targets **outside** active
  proposal paths, only after validation, publication, and retained evidence
  support the claim — and only inside the owning child, never the parent.
- Generated effective prompt/projection assets are consumed only through
  freshness-checked handles and remain derived-only; full prompt expansion
  requires an explicit allowed trigger with retained replay evidence.
- The parent creates no new mechanism, lifecycle gate, routed workflow mode, or
  command facade; it composes with (never modifies or duplicates) readiness and
  surface-architecture audit doctrine.
- Fail closed on missing source, digest mismatch, stale freshness, blocked or
  stale child, or any authority-boundary violation.
