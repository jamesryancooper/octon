# Target Architecture

## Decision

Proposal Program Delivery is the canonical downstream continuation for an
accepted proposal program after lifecycle gates and child-owned receipts are
ready. The workflow may coordinate the route order and emit an aggregate
delivery receipt, but it must not become the authority owner for child packet
receipts, archive relocation, generated publication, repo hygiene deletion,
Git mutation, branch cleanup, final sync, or terminal proof.

The target state is a surface refactor across delivery workflow stages, command
and skill operator surfaces, default Change closeout policy, and closeout route
handoff text. It clarifies how the delivery workflow consumes runner handoff
evidence and then delegates each material effect to the owning route.

## Current Assumptions

- `.octon/framework/orchestration/runtime/workflows/meta/proposal-program-delivery/workflow.yml`
  already defines Proposal Program Delivery as an active, mutating workflow with
  aggregate receipt outputs and a retained readiness preflight.
- The current workflow already names child receipt preservation, generated
  output non-authority, closeout-change Git ownership, archive ownership, and
  repo-hygiene cleanup ownership. The planned implementation should tighten
  handoff semantics rather than create a second delivery authority plane.
- `closeout-change` owns singular Change route selection, hosted no-PR landing,
  branch cleanup authorization, final sync, terminal proof references, and the
  evidence-backed lifecycle outcome.
- `closeout-worktree` owns dirty-worktree decomposition and may return
  non-authorizing proposal-program handoff reports, but it must not replace
  child closeout receipts or singular Change receipts.
- `default-work-unit.yml` and `change-closeout-state-machine.yml` already
  define cleaned as the default requested closeout target while preserving
  evidence-based downgrade when terminal proof is incomplete.
- Generated effective outputs and proposal registry projections are derived
  only. They may be regenerated by owning publishers after implementation, but
  they must not authorize delivery, closeout, archive, or cleanup.

## End State

The delivery workflow executes the following evidence-backed sequence:

1. Bind a delivery profile that records target outcome, PR policy, order
   policy, stash policy, release state, operator grant context when supplied,
   and non-authority boundaries.
2. Run a retained readiness preflight before expensive lifecycle continuation,
   publication checks, archive routing, Git mutation, landing, sync, cleanup,
   branch deletion, or terminal proof.
3. Validate the accepted program and child scope from repository state, using
   fresh review and child receipt digests rather than parent summaries.
4. Run or resume child lifecycles only through their owning packet routes, then
   validate child implementation conformance and drift/churn receipts directly.
5. Validate feature catalog drift before parent closeout, delivery, terminal
   proof, or cleaned claims.
6. Route packet closeout and archive handoff through lifecycle-owned packet and
   archive routes; delivery may observe their receipts but cannot relocate
   archives directly.
7. Route dirty or stale source posture to closeout-worktree, and route coherent
   Change material to closeout-change with explicit include/exclude paths,
   target outcome, validation floor, rollback posture, and source receipt refs.
8. Require closeout-change to own branch-no-pr hosted preflight, governed
   landing authorization, hosted mutation, branch cleanup authorization, final
   sync, terminal proof references, and actual lifecycle outcome.
9. Route eligible local run or artifact residue to repo-hygiene-cleanup through
   its classify-first, receipt-backed helper path. Delivery and closeout-worktree
   may cite that route but do not delete residue themselves.
10. Emit an aggregate delivery receipt and compact evidence index only after
    all source receipts are cited by path or evidence ref and the highest
    claimed outcome is supported by current owning evidence.

## Evidence And Boundary Rules

- Delivery readiness preflight evidence is retained workflow evidence only. It
  narrows route continuation and records blockers; it does not authorize Git,
  archive, cleanup, branch, or generated-publication mutation.
- Child packet receipts remain target-owned. Delivery receipts, parent
  summaries, readiness projections, and compact evidence indexes may cite child
  receipts but cannot satisfy them.
- Closeout-worktree reports are non-authorizing handoff context unless they
  delegate a coherent candidate to closeout-change or repo-hygiene-cleanup.
- Closeout-change receipts are the source of truth for actual Change lifecycle
  outcome, branch landing, cleanup authorization, final sync, rollback handle,
  and terminal proof references.
- Terminal current-state proof is evidence-only and must be fresh after the
  final landing, cleanup, generated publication, proposal artifact, and residue
  classification mutation before delivery may claim `cleaned`.
- The aggregate delivery receipt must report the highest outcome supported by
  current owning evidence and must name the next owning route for every blocker.

## Rollback And Closeout

Pre-implementation rollback is packet rejection, supersession, or archive with
this packet still non-authoritative. Post-implementation rollback belongs to the
implementing Change and must revert workflow, command, skill, closeout policy,
and generated publication changes atomically enough to restore the previous
delivery and closeout handoff behavior.

The packet can be accepted only after a later review-packet pass records an
accepted verdict and implementation authorization. The implemented result can
close out only after implementation conformance, post-implementation
drift/churn, generated publication freshness, Change closeout, archive, cleanup,
and terminal proof evidence validate through their owning gates.
